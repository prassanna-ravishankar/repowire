\begin{abstract}
Coding-agent sessions run in separate repositories and on different runtimes. Coordinating them requires an address for each session and a way to deliver messages into it. We present \sys, a local daemon that connects Claude Code, Codex, OpenCode and Pi sessions through a common protocol. The daemon assigns peer identities independently of display names and runtime sessions. Runtime bridges deliver messages through native input APIs. Only requests require explicit closure; notifications do not. Liveness repair runs on incoming requests rather than a periodic timer. Human control surfaces and orchestrator sessions use the same protocol as other peers. We study one operator's deployment over 146 calendar days, containing 2,810 requests and 370 agent names across 86 projects. One name appears over 144 days and 49 registrations; the median lifetime in the other-agent registration class is 12.6 minutes. Recorded request closure is 87.4\% in the Python era and 98.1\% in the Go era. Of agent-to-agent requests, 52\% cross runtimes. Among requests with a preceding request from the same sender, 74.7\% repeat its recipient. Human surfaces originate 53.5\% of non-machine requests and no notifications. A separate written record contains 76 incidents, of which 34 concern identity, liveness or delivery. \sys{} is open source.
\end{abstract}

\section{Introduction}
\label{sec:intro}

A developer working across repositories may run a separate coding-agent session in each repository. When a task crosses a repository boundary, the developer relays questions and answers between sessions \citep{vibebottleneck2026}. These relays require the developer to preserve details such as flags and version numbers. Shared documentation and task summaries provide context in advance, but must be updated when the underlying code changes.

An agent can instead ask the session working on the relevant repository. The system must resolve the recipient's address even after reconnects or restarts and deliver the question through that runtime's input interface. It must also record whether the recipient answered.

\sys{} runs as a daemon on the developer's machine. Agent sessions register as \emph{peers}. The daemon routes messages to their native input interfaces and records the exchanges in a journal. A Telegram bot, a Slack bot and a web dashboard register with the \code{human} role. An \emph{orchestrator} is a peer that coordinates work through the same message protocol.

The design changed in response to operational failures. Early versions routed by display name and terminal pane. The operator's notes record 76 incidents, including stale registrations and messages delivered to the wrong session. We describe the mechanisms introduced to address these failures and use the journal to measure the resulting deployment.

\paragraph{Contributions.}
\begin{enumerate}
\item A design for persistent, addressable coding agents across runtimes (\cref{sec:design}): daemon-minted identity with a proof hierarchy and terminal retirement; a protocol in which only asks have a lifecycle; bridges under a transport-neutral router; lazy repair instead of liveness polling; humans and orchestrators as peers.
\item An open-source implementation (\cref{sec:impl}) that grew from 5 to 33 tools and from one runtime to six over ten months, with journal schemas that differ across the native cutover.
\item A measurement study of the mesh from its journal (\cref{sec:eval}): 146 days, 2,810 requests, 2,472 agent registrations. We report lifetime and identity churn, closure and latency, the sender-recipient structure of traffic including the human's share, cross-runtime use, the review loop, and incidents coded against the MAST taxonomy \citep{cemri2025mast}.
\item Design lessons (\cref{sec:lessons}) stated as claims with the evidence that supports or limits them.
\end{enumerate}

The study covers one mesh operated by the author (\cref{sec:limits}). The journal records sender and recipient identities, request closure and registration activity. Prior studies examine coding agents through repository activity \citep{agarwal2026velocity,mazloomzadeh2026prs}, practitioner surveys \citep{pan2026measuring}, or collaborative tasks \citep{khatua2026cooperbench}. Our measurements concern a deployment used across successive tasks and sessions.

\section{Setting and Goals}
\label{sec:setting}

\paragraph{The operator's situation.}
One developer maintains several repositories (a product, its infrastructure, a few libraries, a website) and runs a coding agent in each. The agents are on different runtimes because the runtimes have different strengths and separate usage quotas. Work arrives from a phone, a laptop, or a scheduled job. Sessions are long-lived in intent and short-lived in practice: terminals close, laptops sleep, runtimes are upgraded, daemons restart.

\paragraph{Goals.}
\begin{description}
\item[G1 Address.] A session has a stable address that survives reconnects and daemon restarts, and that no other session can take by sharing a path or a name.
\item[G2 Deliver.] A message to a live session reaches its native input, and the sender learns whether it did.
\item[G3 Heterogeneity.] Runtimes differ in hooks, session models and input paths; the protocol must not.
\item[G4 Humans as peers.] The person is addressable and addressed by the same primitives as agents, from a phone.
\item[G5 No polling.] Agents do not send liveness heartbeats.
\item[G6 Record.] Every request, reply, registration and repair is journaled so that the mesh can be debugged and, later, measured.
\end{description}
G5 follows an incident in which timer-driven reconciliation marked live peers offline. Request-triggered repair can leave stale entries until another request arrives (\cref{sec:lazy}).

\subsection{Peers, circles, roles}

A \emph{peer} is one running agent session: a display name derived from its working directory and runtime (\code{torale-codex}, suffixed on collision to \code{torale-2-codex}), a working path, a runtime (\emph{backend}), a status (online, busy, offline), a per-turn state, a free-text description the agent sets, and a last-seen time. A \emph{circle} is a routing scope that by default maps to a terminal multiplexer session, so agents started together can address each other and agents started elsewhere cannot. A \emph{role} is metadata: \code{agent} by default; \code{human} for control surfaces; \code{orchestrator} for a coordinating session; \code{service} for the job runner and the relay. Roles that bypass circles may name a circle explicitly; an ordinary agent cannot.

\subsection{Identity}
\label{sec:identity}

The daemon routes by a minted \code{peer\_id}. Display names, working paths and runtime session ids cannot establish identity on their own. Names collide across circles. Sibling terminals and subprocesses share paths. Runtime session ids can be reused on resume and are absent on some runtimes. The incident record includes failures involving these alternatives (\cref{sec:incidents}).

\paragraph{Proof hierarchy.}
A registration or reconnect claiming an identity is resolved against evidence in a fixed order (\cref{tab:proof}). A live process id on the same machine, runtime and compatible path is the strongest evidence a registrant carries: several registrants describe the same agent independently (a session-start hook, the tool server's lazy registration, a socket reconnect), and all of them converge on the peer already registered for that process. A short-lived \emph{birth certificate} minted at registration lets the tool server adopt the identity without a path search. Path and name are hints only; they filter and allocate names but never prove identity, and the daemon refuses ambiguous matches.

\paragraph{Lifecycle.}
\Cref{fig:lifecycle} shows the states. A clean quit, a hook reporting that its agent process exited, a pane takeover, or three consecutive negative liveness verdicts \emph{retire} the identity: the daemon severs its socket and refuses any reconnect claiming the id unless the claim carries a live process id. Retirement records persist across daemon restarts, so an orphaned reconnect loop cannot resurrect a dead peer. A fresh session start always carries a live process id and reclaims the name cleanly. Retirement prevents a dead session's supervisor from recreating its registration through repeated reconnects.

\paragraph{Restart.}
On daemon start, a one-shot \emph{hydration} pass recreates peers for panes that were alive while the daemon was down, but only when daemon-written pane metadata names the same \code{peer\_id} and the runtime, normalised path, live pane working directory and live process id all agree. Hydrated peers are offline until a socket connects; the daemon does not assume delivery it cannot observe. Unproven panes stay unadopted and are listed for explicit linking by the operator.

\paragraph{Descriptions and sessions.}
A peer's \emph{description} is agent-set task state with no expiry; each turn is shown the current value and asked to update it. A \emph{session} is the durable context behind a peer: a binding from the daemon's session id to the runtime's own session id, which permits resume after the executor is gone.

\subsection{Message protocol}
\label{sec:protocol}

The daemon routes four message types, chosen by lifecycle rather than content.
\begin{itemize}
\item \code{ask(to, text)} is non-blocking and returns a correlation id. The recipient closes it with \code{ack(id)} (seen), \code{ack(id, reply)} (reply delivered to the asker), or \code{decline(id, reason)}. Follow-ups chain with \code{ask(reply\_to=id)}. Until it is closed, the recipient sees a reminder at the start of every subsequent turn. Only a real tool call closes an ask; prose mentions do not.
\item \code{notify(to, text)} is fire-and-forget with no lifecycle.
\item \code{broadcast(text)} fans out within the sender's circle.
\item A \emph{structured question} is an ask with a typed envelope (choice, text, tool permission) answered through \code{answer}; tool-permission questions deny on timeout.
\end{itemize}
Peer-originated deliveries are framed so that a runtime can distinguish them from its user's instructions; messages from human surfaces are framed as user instructions. An ask to a peer the runtime says cannot accept direct input (a sub-agent thread) is refused before any state is created. Replies always reach the asker regardless of circle, because the route was fixed at ask time.

An ask remains open until an explicit close operation. Notifications create no tracked obligation. Human surfaces sent only asks in the observed journal; agent peers used both types (\cref{sec:traffic}).

\subsection{Bridges and transports}
\label{sec:bridges}

A \emph{bridge} translates between a runtime's session API and the peer protocol. Claude Code uses lifecycle hooks and an authenticated inbox for inbound delivery. A stdio shim supplies its identity when proxying tool calls to the daemon. Codex uses a supervised companion on the App Server socket to register threads and steer active turns. OpenCode and Pi load a plugin or extension inside the runtime. A \emph{transport} is the delivery path exposed by a bridge. Failed native delivery produces a failure receipt; the bridge does not fall back to terminal keystrokes. The router resolves a peer before passing the message to its transport.

\subsection{Lazy repair}
\label{sec:lazy}

Liveness reconciliation runs while the daemon handles requests, at most once per 30 seconds. Clean quits deregister through a session-end hook. A socket supervisor reports an agent process exit, and repair checks for inconsistencies missed by these paths. The registry can therefore be stale until a request triggers repair. The daemon emits a \code{peer\_contradiction} event on a transition to an inconsistent state, such as online status without a socket or a missing pane. An operator can also request reconciliation and inspect reachability and open asks. This policy replaced timer-driven reconciliation after a spurious signal marked 43 peers offline (\cref{sec:incidents}).

\subsection{Humans and orchestrators as peers}
\label{sec:humans}

Control surfaces register with the \code{human} role, bypass circles, and use the same four message types. A message from the phone arrives at an agent as a user instruction; an agent's reply to the phone is an \code{ack} with text. Structured questions render as buttons. A \emph{human inbox} (October 2026) queues asks addressed to the human across surfaces.

An orchestrator is a peer with \code{role=orchestrator}; coordination is performed by the session. It is a long-running session the operator addresses from a phone, which scans a board, dispatches asks or durable jobs to project peers, tracks replies, requests reviews, and closes out. Its workspace holds communication preferences, project scope, and memory files; the daemon performs a bounded lexical recall over them and prefixes matching entries to inbound messages. A second orchestrator can coexist as an observer.

\subsection{Schedules, jobs, and the journal}

A \emph{schedule} delivers a future message (notification or tracked ask). A \emph{job} is a durable work record with its own executor: for a job fire, the daemon dispatches an ask from a built-in \code{@jobs} peer, arms the fire when the executor's turn carrying the marker begins, and completes it from the executor's next assistant turn, so results are captured structurally rather than self-reported. An executor that dies with a fire in flight fails it with \code{executor\_died}; a delivered fire is never reaped by a clock.

The journal (G6) is an append-only event table in SQLite plus a per-message delivery-trace ledger recording each stage (created, delivered, closed) with resolved ids and status. It exists so that a misroute can be diagnosed from fields rather than ad hoc logs. \Cref{sec:eval} uses it as the measurement instrument.

\section{Implementation}
\label{sec:impl}

\sys{} is a single Go binary (daemon, CLI, hooks, bridges, tool server, Telegram and Slack clients, relay client) with an embedded dashboard; the first eight months were Python, and the native cutover (PR \#382, 10 August 2026) splits the journal into two eras with different schemas (\cref{sec:method}). State is SQLite with versioned migrations, which date the journal's own surfaces: event journal (22 May 2026), tracked work (25 May), delivery traces (30 May), retired identities (11 June), peer provenance (18 September), routing decisions (11 October), human inbox (13 October). The tool surface grew from 5 tools in December 2025 (\code{ask\_peer}, \code{notify\_peer}, \code{broadcast}, \code{list\_peers}, \code{register\_peer}) to 33 in October 2026, with the largest step (8 to 28) in May 2026 when asks gained lifecycle (\code{ack}, \code{answer}, \code{ask\_many}), jobs and schedules arrived, and the orchestrator role was introduced. Six runtimes have registered peers; Gemini CLI and Antigravity were later retired as supported backends. A hosted relay tunnels dashboard and socket traffic so that a mesh on a home machine is operable from elsewhere; remote agents can join through a relay-side tool server. The repository has 828 commits and 362 pull requests from December 2025 to October 2026, including 18 pull requests from external contributors, and is Apache-licensed. \todo{artifact URL}

\section{Evaluation}
\label{sec:eval}

We measure registration lifetimes and restart activity (\cref{sec:lifecycle}), request closure (\cref{sec:closure}), traffic by sender and recipient (\cref{sec:traffic}), and cross-runtime use (\cref{sec:hetero}). We then examine the written incident record (\cref{sec:incidents}).

\subsection{Method and data}
\label{sec:method}

The data are a backup of the daemon's state database taken on 14 October 2026 and opened immutable; the daemon log, from which only start markers were extracted; the repository's history and pull-request record; and the operator's written notes (project file, 150 orchestrator memory files, 46 vault notes, two repository memory directories), from which incidents were compiled. Configuration and credential files were not read. The journal spans 22 May to 14 October 2026 (146 calendar days; 93 with any event; 64 with an active agent peer). It changes shape at the native cutover: era A (22 May to 10 August, Python) journals asks as events and replies as notification text, and has no registration events; era B (10 August to 14 October, Go) has registration and status events, typed ack events, and the delivery-trace ledger. Asks are unified across eras (2,810: 1,505 machine dispatch from the job runner, 1,305 other). We report per era where the measure depends on the schema. Sender classes: \emph{human} (Telegram, dashboard, Slack, inbox), \emph{orchestrator} (role or name), \emph{peer} (other agents), \emph{machine} (job runner), \emph{relay} (remote tool server). Scripts and the backup copy are kept with the paper's working files; the backup is not released because ask text contains the operator's private material. \Cref{sec:limits} lists what the journal cannot answer.

Two regimes are visible: May and June, when the mesh ran many agents and a job runner (925 of June's 1,321 asks are machine dispatch; July is almost entirely machine), and August to October, when the native daemon ran a smaller mesh without jobs. These periods differ in both traffic volume and workload; the era comparison does not control for those differences.

\paragraph{Names persist.}
Seven display names span 138 to 144 days of the 146-day calendar window. The name \code{repowire-claude-code} appears over 49 registrations, \code{orchestrator-claude-code} over 37, \code{repowire-codex} over 30, and \code{torale-codex} over 3. Senders address these names; the daemon resolves them to current registration ids. Reuse of a name does not establish continuity of a runtime session.

\paragraph{Restarts.}
Daemon restarts are not journaled, but in era B they are dated from the log: 64 starts on 14 days, 58 of them within five minutes of a burst of five or more \code{peer\_online} events, and 41 of 60 such bursts within five minutes of a start. In era A, 243 job rows were failed by restart reconciliation at six distinct minutes: these rows record reconciliation failures, not a count of processes killed.

\paragraph{Contradictions and repair.}
Lazy repair recorded 428 contradictions across the span (online without a socket 130, pane missing 126, agent process dead 5, uncoded 167) and 485 reaps, all by offline time-to-live. Offline reasons in era B are dominated by clean session end (226) and missing socket plus missing pane (115); transport failure accounts for 32. This is 2.9 recorded contradictions per calendar day across the 146-day window.

\subsection{Closure and latency}
\label{sec:closure}

Of 1,305 non-machine asks, 1,169 have a close record and 136 do not (131 in era A, 5 in era B). Recorded closure rose from 87.4\% in era A to 98.1\% in era B (\cref{tab:closure}). The design includes retirement of dead identities, explicit delivery-failure receipts and queued redelivery to a reconnecting orchestrator. Five era B asks closed with \code{send\_failed}. The era comparison does not isolate the effect of any mechanism. Expiry is not journaled, so the open duration of the 136 unclosed asks is unknown.

Latency is time to acknowledgement, which in practice often precedes completion (``on it''); it is not task duration. The median is 26 to 29 seconds in both eras, p90 about three minutes. By sender, the human is acknowledged fastest (median 23 s, p90 105 s), peers in 38 s, the orchestrator in 40 s with a p90 of 8.3 minutes.

\paragraph{Human traffic.}
Human surfaces originate 53.5\% of non-machine asks over the span and no notifications. Their monthly share ranges from 17\% to 60\%. Only seven asks run from agents to human surfaces. Agents also send ack replies and notifications, but the notification counts here classify senders, not recipients: orchestrators and peers sent 1,635 notifications in May and June.

\paragraph{Orchestrator traffic.}
Human-to-orchestrator is the largest flow, at 33.4\% of non-machine asks. Peer-to-peer requests account for 26.7\%. Asks sent by orchestrators rose from 11\% of non-machine traffic in May to 23\% in October. These shares describe the use of the protocol in this deployment.

\paragraph{Repeated recipients.}
We measure repetition over non-machine, non-self asks with a resolved recipient id. Senders are keyed by \code{peer\_id}, except that all human surfaces form one sender. Of the 1,159 asks with a preceding ask from the same sender, 866 (74.7\%) name the same recipient. Monthly shares range from 0.50 to 0.86. The repeat share is 0.859 for the human, 0.651 for peers and 0.423 for orchestrators. The companion routing study \citep{routerpaper2026} uses a different definition: the last exchange in either direction, a 24-hour expiry and an online worker recipient. Its recency rule matches 333 of 555 recipients (0.60); that population is not a subset of the repetition measure here.

\subsection{Cross-runtime traffic and review}
\label{sec:hetero}

Of 591 agent-to-agent asks, 307 (52\%) cross runtimes. The recorded pairs include 177 from Claude Code to Codex, 104 in the reverse direction, 13 from Codex to Pi and 9 from Codex to Antigravity. Message-text matching identifies review traffic for 64 of the 152 repository pull requests opened during the journal span; 37 have a verdict message. Thirty have a requester and reviewer on different runtimes or verdicts from two runtimes (23 Claude Code requesters with Codex reviewers and 7 in the reverse direction). Among the 37 PRs with a verdict, 27 have one observed review round, 5 have two, 3 have three and 2 have five or more; all were merged. Some review messages postdate merge, so these counts do not establish that each review preceded it. The operator's notes estimate about 12 orchestrator turns and 30k tokens for a mediated three-round review, with about 75\% saved by direct peer review. These estimates were not measured from the journal. Separately, over the repository history, the automated review bot produced 714 inline findings on 284 PRs; 80\% carry a medium-severity badge.

\section{Lessons}
\label{sec:lessons}

\paragraph{Registration identity.}
The 34 identity, liveness and delivery incidents motivate separating a routable registration from its display name and runtime session. In \sys, the daemon assigns ids, checks process evidence during adoption and records retirement. Gastown also separates persistent worker identity from sessions \citep{gastown2026}; Claude Code Agent Teams documents limitations on in-process teammate resumption \citep{agentteams2026}. The observed closure increase does not establish which identity or delivery change caused it.

\paragraph{Request tracking.}
The ask/notify split matches the recorded traffic: humans originate asks, while agents send both asks and notifications. Explicit closure and reminders make open requests inspectable. The journal does not measure how much either mechanism contributes to the closure rate.

\paragraph{Request-triggered repair.}
Lazy repair avoids the periodic reconciliation path implicated in the mass-offline incident. It leaves registry entries stale until a request or runtime event updates them. The journal records 428 contradictions, but does not measure a bound on detection delay.

\paragraph{Recipient repetition.}
Human senders repeat their previous recipient in 86\% of eligible asks, compared with 42\% for orchestrators. A routing evaluation should report switches separately so that repeated recipients do not dominate its score \citep{routerpaper2026}.

\paragraph{Scope.}
The design addresses registration and delivery across successive sessions. The traffic shares and recipient repetition describe one operator's deployment. They do not estimate how other operators would use the same protocol.

\section{Related Work}
\label{sec:related}

\paragraph{Task-spawned multi-agent frameworks.}
CAMEL, MetaGPT, ChatDev, AutoGen and OpenHands study coordination among agents within an application or task \citep{li2023camel,hong2024metagpt,qian2024chatdev,wu2023autogen,openhands2024}. MAST analyses failures in multi-agent execution traces \citep{cemri2025mast}. Our incident record concerns a deployment across successive sessions, including registration and delivery failures. \todo{Check the framework comparison against supported persistence and human-interaction features.}

\paragraph{Coding-agent fleets.}
Claude Code Agent Teams uses a lead session and teammate sessions with shared tasks and messaging; its documentation lists in-process teammate resumption as a limitation \citep{agentteams2026}. Gastown separates worker identities from sessions and provides lifecycle supervision \citep{gastown2026}. Cursor reports contention and coordination failures in a shared-file design before introducing separate planners and workers \citep{cursor2026}. \sys{} routes messages across runtimes and admits human control surfaces as peers.

\paragraph{Protocols.}
\sys{} exposes tools to runtimes through MCP. Interoperability surveys describe discovery and task exchange through MCP, ACP, A2A and ANP \citep{ehtesham2025survey,mcp2025survey}. Our design concerns the local registration evidence and runtime input paths required to deliver messages to coding sessions. \todo{Compare lifecycle and delivery semantics against versioned protocol specifications.}

\paragraph{Measurement.}
Pan et al.\ \citep{pan2026measuring} study deployed agents through interviews and a practitioner survey. Repository studies examine agent contributions and their evolution \citep{agarwal2026velocity,mazloomzadeh2026prs,msr2026survival}. CooperBench evaluates collaboration between coding agents \citep{khatua2026cooperbench}. Our journal records communication and registration activity in one deployment; it does not measure task quality. The companion paper discusses routing and delegation benchmarks \citep{decisionbench2026,orchbench2026,routerbench2024}.

\paragraph{Persistent state.}
InfiAgent reconstructs context from file-backed state \citep{infiagent2026}, while Omri et al.\ characterise agent memory systems \citep{agentmemory2026}. \sys{} stores orchestrator memory and runtime session bindings outside the current prompt. The learned-recall experiment is reported separately.

\section{Limitations}
\label{sec:limits}

The author operates the only mesh studied. Traffic structure may reflect that operator's habits. Incident counts depend on note density and are not failure rates. Era A has no registration events or delivery traces; 855 of the 1,169 close records depend on parsed notification text. The log cannot date most earlier daemon restarts. Ask expiry is not journaled, so 136 asks have no measured close time. Acknowledgement does not establish completion. Shared commit credentials prevent attribution of code to agents or the human. Reviews conducted only in a terminal or on GitHub are absent from the mesh review count. Fifty-three calendar days have no journal event. Runtime costs are not recorded. The private backup cannot be released; the scripts and aggregate tables are intended for the artifact. \todo{artifact release}

\section{Conclusion}

\sys{} connects coding-agent sessions through a daemon that resolves peer identities and delivers messages through runtime bridges. Humans and orchestrators use the same request protocol. The journal records communication across six runtimes and substantial reuse of names across registrations. The incident record documents failures in identity and delivery that informed the current design. Recorded request closure increased from 87.4\% to 98.1\% across the Python and Go eras, but the observational comparison cannot attribute that change to individual mechanisms.

\section{Incident examples}

One incident per class from the written record, dated by note text.
\begin{itemize}
\item \textbf{Peer leak or phantom} (2026-05-15): an ack from a retired orchestrator registration, absent from the peer list, arrived as a live request to merge an already-merged pull request.
\item \textbf{Misroute} (2026-05-14): during co-orchestration, a project peer received three of its last four asks intended for others, and a reply addressed to a suffixed name fell back to broadcast. Fixed by the reconnect identity check.
\item \textbf{Delivery drop} (2026-05-11): a reply sent on an already-closed ask returned success and was not delivered.
\item \textbf{Daemon restart disruption} (2026-05-10): repeated restarts during installer testing cleared in-memory ask state; stale reminders surfaced and pane kills were refused for pre-restart peers.
\item \textbf{Config drift} (2026-05-19): the installed CLI lacked a command present in the checkout; a forced reinstall left stale packages.
\item \textbf{Job or schedule} (2026-06-11): a job fire never armed because the executor's turn carried no marker; the fire stayed delivered.
\item \textbf{Auth expiry} (2026-06-04): a workspace token rotated to a scopeless state; after re-authentication a stale cache kept calls failing.
\item \textbf{Other} (2026-05-15): one peer wrote files into another peer's worktree and switched its branch.
\end{itemize}
