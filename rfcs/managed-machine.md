# Managed is another machine

Status: phase 1 in progress (2026-10-25); phases 2 to 4 need their own design.
Builds on the managed control plane (`feat/managed-relay`, `feat/managed-web`)
and the hosted runtime (`feat/hosted-runtime`, `feat/hosted-backend`).

## Problem

Managed agents exist in two shapes today:

- **Daemon-owned.** `spawn_peer(backend="hosted")` creates the agent on the
  Worker and registers it as a peer on one daemon. Mesh tools and results
  travel over that daemon's gateway socket, so the agent's mesh presence dies
  with the laptop.
- **Web-created.** `/managed` creates the agent directly on the Worker. It has
  no mesh identity at all (`home_machine: null`, "not on mesh").

Two kinds of agent, and a UI that explains the difference. Separately, the
relay knows every machine an account has connected, but machines cannot reach
each other's agents: the relay drops inter-daemon frames on purpose
(`relayserver/server.go`, covered by a regression test), and the daemon
handles only HTTP tunnel frames.

## Idea

To the relay, a **machine** is something with an id that answers a canonical
request API: list agents, ask, notify, wait for a reply, list open requests.
Today every machine is a daemon. Managed becomes one more machine, `managed`,
always online, reached over HTTPS with the relay's control credential and the
caller's owner id.

Each machine is the hub for its own peers: it decides identity, access and
delivery. The relay authenticates, names the owner and the machine, and
forwards. It never decides access.

## Phase 1: managed is a machine for the relay's request API

Scope: the relay MCP tools (`list_machines`, `list_agents`, `ask_agent`,
`send_message`, `get_reply`, `list_requests`) and the managed web view. The
cookie dashboard tunnel, event streams and session shares stay daemon-only;
they keep selecting a daemon as today and never select `managed`.

Relay:
- A `machine` interface with typed methods (`Agents`, `Agent`, `Ask`,
  `Notify`, `Wait`, `Pending`) and two implementations: the daemon tunnel
  (today's code moved behind it) and the managed client.
- `list_machines` includes `{daemon_id: "managed", kind: "managed"}` when the
  managed service is configured. Daemon rows gain `kind: "daemon"`.

Which agents are on `managed`: those created on the Worker directly (web or
relay), `home_machine` null. Daemon-owned agents stay with their daemon until
phase 4 migrates them, so one runtime never has two ask authorities. Retired
agents leave discovery; their requests stay readable.

Worker (owner DO), a durable `requests` record, control credential only:

| Field | Meaning |
| --- | --- |
| `id` | public request id, generated by the relay (`rq-` + 32 hex), owner-unique; also the run's operation id |
| `agent`, `kind` | target agent; `ask` or `notify` |
| `requester` | immutable principal named by the relay (`relay-mcp-<grant>`), never by the body of a model or end user |
| `text`, `created_at` | what was sent and when |
| `state` | `submitting` until the runtime accepts it, then `accepted` |

The result is the run row of the same `(agent, id)`: status, reason, and the
answer text, which the run log now keeps.

Routes:
- `POST /requests {id, agent, kind, requester, text}`. A known `id` returns its
  existing receipt before any budget or retirement check; a known id with a
  different body is 409. Otherwise 404 unknown agent, 410 retired, 402 over
  budget: definite refusals, nothing recorded. On a submit error the request
  stays `submitting` and the relay reports the outcome as uncertain with the
  id, so `get_reply` can settle it; it never invites a resend.
- `GET /requests/{id}?requester=&wait=0..20`: the daemon wait contract,
  `{status: "pending"}` or `{status: "resolved", close_reason, reply,
  responder}`. `close_reason` is `answered`, `not_delivered` (the runtime
  never admitted it), or the run's unanswered reason (`aborted`,
  `step_limit: …`, an error). 404 unless `requester` matches.
- `GET /requests?requester=`: that requester's unsettled asks
  (`request_id, to_agent, message, created_at`). Notifies are not listed.

Ask text reaches the agent as `<peer-message from="@<requester>" type="ask"
correlation-id="<id>">`, the same trust boundary the daemon applies.

Runs record who submitted them (`via: daemon | control`). Only the daemon's
runs go to its outbox; the `web-` operation prefix rule goes away, kept only
for records written before `via` existed.

## Phase 2: one mesh across machines (needs design)

Requirements surfaced in review, to settle before building:

- **A new protocol, deliberately.** Prefer forwarding the canonical request
  API over the existing authenticated HTTP tunnel to resurrecting the
  dropped `relay_*` frames; either way the drop test is replaced on purpose.
- **Verified remote principal.** `(owner, machine, peer_id, circle, role)`:
  the source daemon binds peer, circle and role; the relay binds owner and
  machine from the authenticated connection; the receiver rejects a missing
  identity and never resolves it as a local peer. A managed agent's principal
  comes from its DO config, never from model arguments.
- **Circles are logical, per owner (decided 2026-10-26).** A circle spans
  machines: peers on different machines in the same circle reach each other
  as if local. The receiving machine enforces circle access against the
  verified remote principal. Consequences to design: same-named circles on
  different machines merge (`default` included, unless default stays
  machine-local); a managed agent's circle becomes per-agent config instead
  of the fixed `managed`; broadcast and discovery span machines within a
  circle; any daemon of the owner can vouch for its peers' circles, which is
  acceptable inside one owner.
- **Replay and duplicates.** Wide, namespaced request ids; the receiver
  persists a receipt before delivery and binds sender, target, kind and
  payload to the id, rejecting conflicting reuse. Notifies get delivery ids.
  A lost accept or reply is "uncertain", never rerun on reconnect.
- **Reply ownership.** The target machine owns the request and its result
  (as in phase 1); the source holds a remote-request handle and reads or
  receives the settlement. Managed agents' `ask_peer` replies need an
  admission route that does not depend on a laptop.
- **Directory.** Remote entries are kept separate from locally executable
  peers and addressed internally by `machine + peer_id`; `name@machine` is
  presentation only.

## Phase 3: mailbox (needs design)

Store-and-forward for offline machines: expiry, acknowledgement boundary,
tombstone retention, ordering, and access revalidation at delivery. The relay
runs as one replica today with per-replica SQLite; the mailbox needs that
settled first (single replica, or shared storage). Scheduled jobs on managed
agents run from Durable Object alarms so they fire with the laptop off.

## Phase 4: retire the daemon's direct link

`spawn_peer` and `job_create` target `managed` through the relay; the daemon's
hosted backend, gateway socket and `hosted.*` config go away. Existing hosted
peers migrate to remote peers on `managed` atomically, with one ask authority
at every point. Until then the Worker keeps one daemon socket per owner.

## Non-goals

- Cross-owner messaging.
- A second router in the relay.
- Moving same-machine traffic through the cloud.
